## Architecture recommendation and evidence

Retain the existing plain-JavaScript UI and working offline flows. Extract domain commands and persistence in small slices; a framework rewrite would add unrelated migration risk. New money/stock features should use immutable movements plus projections, with an explicit baseline for incomplete legacy history. This is an engineering recommendation based on this application's coupled ledger/stock requirements, not a claim that every POS needs a general-purpose accounting engine.

Postgres/Supabase is a provisional fit because related stock, payment and audit effects can be committed together and authorization can live below the browser. RLS must be paired with correct grants and restricted server functions; privileged service credentials stay off the client. [Supabase authorization documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

Supabase documents a local stack and version-controlled migrations, which supports proving behavior before provisioning a real shop backend. [Local database migrations](https://supabase.com/docs/guides/local-development/database-migrations).

Firebase remains a valid candidate if the owner prefers its ecosystem, but its Firestore documentation distinguishes offline-capable batched writes from transactions, which fail offline. A provider SDK does not eliminate the need to design inventory authority, retries and reconciliation. [Firestore transactions and batched writes](https://firebase.google.com/docs/firestore/manage-data/transactions).

These documentation checks were made on 11 September 2026. No price, quota, regional availability or production security configuration has been assumed; verify the chosen offering at the provider decision gate.
