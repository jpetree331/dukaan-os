# Local stores and stock in transit

Owners retain access to all stores in the local shop book. A reviewed assignment screen explicitly selects each cashier's stores. Saving it enables the storeAccessVersion marker; new staff start with no assigned stores, and adding the first new staff member requires the review first. Until this explicit review, legacy cashiers retain their current-store access and cannot select another store themselves. Staff switching only offers people assigned to the current store; action boundaries and configured-book validation reject a wrong-store actor. These are local application controls, not remote tenant authorization.

Store-specific receipt profiles override shop name, contact/address, GSTIN, UPI address and theme for new sales; each sale snapshots the resulting profile. Daily targets are store-specific and celebration state is keyed by store/day. Existing stores without overrides use the shop defaults. Profile/assignment changes require owner access, with fresh owner verification for assignment and changed payment-address settings. A restored business backup preserves local staff and compatible local cashier assignments, removes assignments to absent stores, and keeps local per-store UPI addresses (falling back to local shop UPI). Imported receipt snapshots retain their original historical identity. Owners review assignments again if restored stores differ.

Dispatch removes sellable stock into an immutable transfer record with original batch cost, expiry and purchase provenance. It neither credits destination stock nor changes cash/debt. The owner explicitly maps to a destination catalog item with matching units, or creates a matching empty catalog item. Expired and quarantined source goods cannot be dispatched. Goods can expire in transit; receipt preserves expiry and therefore does not make them sellable again.

Partial receipt consumes the next unreceived portion of original allocations and creates individually identified destination batches. A repeated command ID with identical contents returns the existing receipt; changed contents and over-receipt reject. Remaining goods can be recalled only in the source store, after they physically return. Recall is a separate receipt against remaining in-transit stock, not cancellation of already accepted goods. To return already accepted goods, dispatch a new reverse-direction transfer.

At every durable step, source on-hand + destination on-hand + in-transit stock changes only for separate sales, purchases, returns or adjustments. Dispatch and receipt stage all affected items and commit the book and command together. A failed save leaves both stores and the in-transit remainder unchanged. Original supplier provenance remains attached; a supplier return can use stock only when it is back in the original purchase's store/item. Current catalog unit changes block receipt with an explicit repair message; existing transfer snapshots remain unchanged.

The UI dispatches one item per short action; the domain command accepts multiple distinct source items atomically. History shows partial receipts and recall notes. Optional root stockTransfers/transferReceipts and profile/access version markers reject older strict readers. Encrypted backups, migration and native journal replay preserve all sides of the transfer. This is single-device local-book settlement: there is no cross-device network delivery, automatic remote acceptance or general warehouse accounting.
